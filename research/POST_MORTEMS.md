# Post-mortems of the research programme

One entry per failure of the programme as a whole, newest first; the misses of the desk's calls have their own file, [`../predictions/POST_MORTEMS.md`](../predictions/POST_MORTEMS.md). Each entry ends in a rule, a test or a changed procedure, and a line in [`../BUILD_LOG.md`](../BUILD_LOG.md). Study verdicts are never edited; the lesson goes here and into the method.

## A detach rule the loop's own shell could not honour (written 2026-11-04)

**The record (observed, from the commit log, the run notes and this run's probes).** The rule of 2 November ("lock and long fetches": anything written before a fetch longer than a minute is committed first, and the fetch runs detached as `setsid nohup … > file &` so that a run cut off while waiting loses only its summary) was written on the morning the 00:15Z run of 2 November ended uncommitted after a fourteen-minute fetch. On 2 November at 06:21Z the first Study 013 snapshot was launched under that rule and finished at 06:25:36Z; how the launching call stayed alive for those four minutes is not recorded (unknown). On 4 November at 12:15Z two probes of the FRED endpoint launched the same way left empty log files and no process, and the fetch was run in the foreground instead. This run (18:16Z) launched four sixty-second jobs from the learning loop's own shell, each writing a dated line every ten seconds, and read their state after the launching call had returned: `setsid nohup … &`, `setsid -f …` and `nohup … & disown` each wrote one line and were gone within sixteen seconds of launch, so the kill reaches a process in a new session and is not a terminal or process-group signal; a transient systemd user unit (`systemd-run --user`, its own control group) and the shell tool's own background mode both ran to completion.

**Consequence.** No record was affected: the 12:15Z fetch took under a second in the foreground and the 2 November snapshot finished. The rule as written would have failed on the next fetch that mattered, Study 013's resolution fetch after 2027-01-20, which reads two files per market over an eight-week sample and takes minutes.

**Why (inferred).** The rule was written from the failure it answered and never run on the shell that would carry it out; a rule that names a command is a claim that the command works, and this one was labelled a rule before it had run once. The organisation's own notes of 17 and 24 October had already recorded that a `nohup` or `setsid` child started inside a tool call dies when the call returns; the rule was written without reading them, so a known failure was prescribed as the fix for another.

**Changes (built and tested 2026-11-04):**

1. [`tools/detach.sh`](../tools/detach.sh): `start <name> <log> -- <command…>` runs the command as a transient systemd user unit in its own control group with the launcher's working directory, its output appended to the log under a dated start line and an end line carrying the exit code, so the next run reads completion from the file alone; `status` and `wait`; a second start under a name still active is refused by the service manager and launches nothing. `--self-test`, in `make lint` and the CI lint job: the unit's control group differs from the launcher's, the start line, the output, the working directory and the end line are in the log, a failing command's exit code reaches the end line, and a duplicate name is refused and does not run; skipped with a line where no user service manager is reachable (the CI runner). Live on this host: pass in 3.3 s; a forty-second job started through it was still running, and still writing, after the launching call had returned.
2. *Rule:* a procedure that names a command is run once on the shell that will carry it out before it is written as a rule, and that run stays as a check; the mission text now names `tools/detach.sh` (or the shell tool's background mode) where it named `setsid nohup`.

**Still open.** How the 2 November launch survived is not recorded; nothing depends on it now.

## A test that passed for the wrong reason, and its twin reviewed the same day (written 2026-11-01)

**The record (observed, from the committed tests and `tools/check_bound_defaults.py` run on `acb49d5`).** The forward modules define their paper-log paths as module constants and their helpers take them as default arguments (`def write_record(record, directory=DECISIONS_DIR)`). A default is evaluated once, at import. A test that does `monkeypatch.setattr(forward, "DECISIONS_DIR", tmp_path)` and then calls `main` has changed the module attribute, not the default: every call inside the module that omits the argument still reads or writes the real folder. On 31 October this was found in Study 006's missing-input test, which had passed locally by reading the real `paper-log/raw/` and printing a wait line where the test expected a refusal; 006's decide step was changed to pass its paths by name and the test to assert the refusal text, and the lesson was filed. The same evening Study 004 got a twin test under a Tester review (eight refusal mutations per study, accept with fixes). A static read of every forward module and its tests this morning found, on the same commit that carried the lesson:

- Study 004's `main` reached `fetch_inputs`, `write_record`, `load_records`, `latest_books`, `append_shadow` and `write_books` through bound defaults (seven call sites). The test patched four constants and asserted refusals on `--dry-run` only, so it never exercised a write. A test that patched the decisions folder and ran `decide` without `--dry-run` would have written into the real `paper-log/decisions/`, left the patched folder empty, and passed. Run before the fix, the new write-path test did exactly that: it was stopped only by the study's never-overwrite rule, because the real folder already held the 30 October record (`FileExistsError` on the real path).
- Study 006's own fix of 31 October was partial: the decide step passed its paths by name, the shadow and interim steps did not (`fetch_alpaca`, `read_shadow` three times, `append_shadow`), and the comment said so as if that were acceptable.
- Studies 007 and 008 (`forward007.py`, `forward008.py`) pass every patched path by name; their tests' patches reach the code. Studies 003, 005, 010, 011 and the desk view inject paths as arguments or do not patch module constants, so the class does not arise there today.

**Consequence.** No record or shadow line was affected: no committed test runs a write through `main` with patched paths, and the loop's runs use the real paths by design. The exposure was to the next test, and to the Tester review's verdict, which examined refusal mutations (does a missing or edited file refuse?) and not the test's reach (does the test's patch arrive where the code reads?). A review that mutates the code cannot see a test that never reaches the mutated line.

**Why (inferred).** The lesson of 31 October was filed as a fact about one test and applied by hand to one entry point, the same shape of error as the 25 October refusal fixed in one copy only: the rule "fixed in every copy in the same commit" was written the day before and still not applied, because "every copy" was read as "every copy of the file", not "every place the class occurs". A mechanical search for the class (every test that patches a constant; every call that omits a parameter whose default is built from it) takes a minute and was not run; the finding was fixed where it was seen.

**Changes (built and tested 2026-11-01):**

1. `tools/check_bound_defaults.py`: for every forward or paper module and its tests, the constants the tests patch (by literal name, in a loop over a literal tuple, or in a loop over a module-level list), the module's functions whose defaults are built from them, and every call inside the module that omits that argument. Any such call fails `make lint` and the CI lint job. Self-test over a passing and a failing fixture. Live before the fix: 13 call sites reached through a default (7 in 004, 6 in 006); after: 0 over 17 modules and 31 patched constants.
2. Studies 004 and 006: every path in `main` is passed by name. A printed path outside the study (a test's folder) is printed as it is instead of raising from `relative_to`.
3. Study 004: a write-path test. With six constants patched, `decide` without `--dry-run` must write its record into the patched folder, the real `paper-log/decisions/` listing must be unchanged before and after, and the shadow step must read from the patched folder (no earlier record there: refusal). It failed before the fix and passes after.
4. *Rule:* a defect class found in one test or one entry point is searched for mechanically across the tree before the commit that fixes it, and the search becomes a check when it can be written as one. A review of refusal behaviour does not establish that a test's patches reach the code; the check does.

**Still open.** `relative_to(STUDY_DIR)` on a printed path remains in 005, 007 and 008 (a display error only, and only when a test writes through `main` into a patched folder; none does today). Studies 005, 010 and 011 call their helpers with bound defaults from `main` without any test patching them; the check is silent there by construction, and a future test that patches them will turn it red.

## A refusal fixed in the newest copy only: the 006/007 dry-run crash (written 2026-10-31)

**The record (observed, from the commit log and the code-review files).** Studies 006, 007 and 008 share one forward entry point by copying: `src/forward.py` of 006 became `src/forward007.py` of 007 and `src/forward008.py` of 008. The separate code review of 008 on 25 October ([`008-bond-value-tilt-long-history/paper-log/CODE_REVIEW.md`](008-bond-value-tilt-long-history/paper-log/CODE_REVIEW.md), should-fix 5) found that `decide --fetch --dry-run` skips the fetch and then reads `paper-log/raw/`, which on a fresh checkout is a `FileNotFoundError`. It was fixed in 008 the same evening (`3d55337`, 23:30 UTC) with a test. The two earlier copies were not touched. The first run of all three on the real clock, the pre-flight of 31 October at 06:18 UTC (the hourly loop never ran a `--dry-run`, and every `--fetch` run happened on a machine where the files already existed), printed a traceback for 006 and 007 and a clean refusal for 008. Found while fixing: 006 also computes its starting holdings from the study's git-ignored `data/raw/` on every run (007 and 008 read theirs from the committed `results/episode/summary.json`), so on a fresh checkout 006's decide step crashed before it reached the forward inputs at all.

**Consequence.** No record was affected: the loop's path (`--fetch`, files present) never hit it. A reader who cloned the repository and ran the documented dry run would have seen a broken tool, on the studies whose first records were already late.

**Why (inferred).** A fix made where the review looked. Three copies of one file, no list of the copies, and a review finding tracked only in the reviewed study's own review table: the fix had nowhere to propagate from. The pre-flight that exercises the no-input path existed only from 31 October; before that, nothing ran the code the way a reader would.

**Changes (built and tested 2026-10-31):**

1. 006's `forward.py` and 007's `forward007.py` refuse with exit 1 and no write when a forward input is missing from `paper-log/raw/` ("run with --fetch") or a frozen input is missing from `data/raw/`, and say that `--dry-run` does not fetch; one test in each study runs `decide --dry-run` against an empty folder and asserts the refusal and that nothing was written (006 also with the frozen folder missing). 008's existing test stays. Suites: 006 and 007 forward tests pass with the new tests; ruff and mypy clean.
2. *Rule:* a code-review finding fixed in one copy of shared forward code is fixed, with its test, in every copy in the same commit, and the review table names the copies; a study that copies a module inherits that module's open findings.

**Still open.** 006's starting holdings should come from a committed frozen starting-state file, as 010's `frozen_hbar.json` and 007/008's episode summary do; the same class of defect as Study 004's forward code reading its last in-sample signal row (private backlog). Not changed in this entry: it alters what a record reads, so it gets a reviewed change before the 2026-11 record, not a patch on the day.

## The slip of 26–30 October, and the month-end that nobody was there to write (written 2026-10-31)

**The record (observed, from the commit log and the loop's run notes).** 213 commits between 00:00 UTC on 26 October and 16:50 UTC on 30 October: 100 on the 26th, 77 on the 27th, 31 on the 28th, 2 on the 29th, 3 on the 30th. By subject (keyword counts, categories overlap): about 76 were hourly "library still on release 202608/202609, not kept" fetch logs for Studies 010 and 011; about 88 touched the front page, the paper dashboard, links, the glance table or wording. Eleven consecutive hourly runs on 27 October (05:15 to 15:15 UTC) each wrote "maintenance-only hour" in their notes; on 28 October, the day outside readers were expected, the runs built five checks of the front page (relative links, glance figures, result sections, "what the desk knows", dashboard currency). From 19:15 UTC on 28 October the loop held for about 45 hours (no work except two date-bound runs) waiting for owner decisions. The owner's reading on 30 October: the last three to five days slipped into polishing, and the point is to learn from mistakes and misses. The learning that did happen in those days was real (the 006–008 leg's fidelity failure, the data-terms trace, the V1 scorer defect found before its first use, the bar-age arithmetic) and the post-mortems of 30–31 October are built from it.

**Consequence (observed): the first month-end forward records were not written when due.** [`../MONTH_END.md`](../MONTH_END.md) and the private backlog's item 0 said "every step is run by the hourly loop from 2026-10-30 21:15 UTC". At about 16:50 UTC on 30 October the loop's cadence changed to four runs a day at the owner's instruction, to stop the polishing; the 22:15 London run that would have written the records no longer existed. The 18:15 run (before the gate) and the 00:15 run (after it) each worked the top item of a queue of learning items; the 00:15 run's own notes say that a later item "waits for the first forward record to be confirmed written", and it did not check whether it had been. The records for signal date 2026-10-30 were written at 06:18 UTC on 31 October, about nine hours after the gate (commit `5b0a24f`): Studies 003, 004 and 005 from the same daily bars that existed on Friday night (no bar exists after the signal date; the execution date 2026-11-02 is unchanged; the delay gained no information), Studies 006–008 as wait lines (FRED had not posted 30 October's H.15 row), 010 and 011 as fetch checks (release 202609 still). The pre-registrations allow a record up to the close of the third NYSE day after the signal date, so no month was lost; that the gap was nine hours and not three days was luck, not design.

**Why (inferred).** Three causes, each on record.

1. *The date-bound list lived in prose and in a schedule.* MONTH_END.md, the backlog's item 0 and the "Next:" line of every run note said what was due; the hourly cadence was what made someone read them. When the cadence changed, the list did not move with it: the instruction for the new mode named a queue of learning items and said nothing about what was due. A list that only one schedule reads is part of that schedule.
2. *The polishing was the loop's answer to an empty queue, not a chosen priority.* From 27 October the programme had no powered question (every freely readable candidate had closed at power first) and every result-bearing item waited on an owner decision. "An empty queue is a signal to plan" was read as "do the next check a reader would run". Each check was useful on its own (two found faults a reader would have seen; all now run in CI) and the sum was 213 commits with no new evidence. The error was the missing stopping rule: nothing said when upkeep should stop and a run should end with nothing.
3. *Polling bound to hope, not to the calendar.* Studies 010 and 011 polled the French library every hour for release 202609 from 12:45 UTC on 26 October until it appeared at 16:16 UTC on 27 October, two commits an hour into the public history. The pause decided at 19:15 UTC on 27 October ("release 202610 must contain October, so it cannot exist before the 30th") could have been made on day one from the calendar.

**What was right.** Every polish commit was honest and reversible, and the three front-page checks are now permanent tests; the hold from 19:15 UTC on 28 October was the right call once the owner's question was open, and the owner's instruction confirmed it; the forward code's own gates meant a late record could not be an early or a rewritten one.

**Changes (built and tested 2026-10-31):**

1. *A due register the loop reads first.* [`../tools/check_due.py`](../tools/check_due.py) computes from the NYSE calendar and the committed files what is owed and whether it exists: the monthly decision records of Studies 003–008 (due 21:15 UTC on the last NYSE trading day of each month; deadline 21:00 UTC on the third NYSE day after), the weekly desk view (Fridays from 2026-10-30), every ledger call past its due date without an outcome, and the state of 010's and 011's release-bound records. It prints `ok`, `not due`, `waiting`, `DUE` or `OVERDUE`, exits 1 on OVERDUE unless the study's `paper-log/missed.csv` logs the miss, and runs in `make lint` and the CI lint job, so a record past its deadline turns the public build red. Self-test over a built fixture (pass; the first version's test asserted the wrong status for a fixture record that existed, found and fixed before the first commit). Every loop run runs it before reading its queue and works a DUE or OVERDUE line first; a due time that falls more than six hours before the next run is a defect to fix, not a reason to wait.
2. *A stopping rule for upkeep.* A run whose only available work is a check, a wording change or a re-verification writes the next post-mortem candidate list and stops; four runs a day, each producing one learning artefact or nothing (the owner's rule of 30 October, now the loop's own).
3. *Polling bound to the calendar.* A source is checked for a release only from the first date on which the release can exist (the library needs the month's last trading day; FRED's H.15 for day t is posted at 16:15 ET); the register's `not due (due …)` lines are the schedule.

**Still unknown.** Whether 006–008's October records will be written before their deadline (FRED's row for 30 October is expected on 2 or 3 November; the register shows `waiting` until then). Whether four runs a day are enough for every date-bound item, or whether the register will show a due time that no run can meet.

## Eleven studies, no edge: what the programme kept choosing (written 2026-10-31)

**The record.** Eleven studies from 2026-10-21 to 2026-10-26: two halted at a data gate before any rule ran (001, 002); five not supported (003, 004, 008, 010, 011); one refuted in-sample (005); two inconclusive (fragile) (006, 007); one pooled forward check pre-registered as a low-power check (009). No rule survived its own robustness test ([root README, "Results at a glance"](../README.md#results-at-a-glance)). The procedure held every time: rules and trial counts fixed before the data, one out-of-sample run, verdicts not re-weighted, separate-session recomputation. The question here is not whether any verdict was wrong. It is why eleven honest tests produced so little information, and what the programme kept doing that made that likely.

**Finding 1 (observed): most of the tests could not have seen the edge the literature makes plausible.** The agenda had the decay numbers before Study 003 ran: a published predictor keeps about 74% of its return out of sample and about 42% after publication ([MP16], [`../RESEARCH_AGENDA.md`](../RESEARCH_AGENDA.md) §2), and the agenda's own inference was that "any signal taken from a paper should be expected to deliver well under half of its published return". The bar was then set at t ≥ 2.0 on the timing difference, with no power computed before the question was fixed, for every study from 001 to 005 (agenda, dated addition of 2026-10-24: "No study so far was chosen by power"); from Study 006 a minimum detectable effect was committed before each question, but against the programme's own 2%-a-year bar or the pool's observed Sharpe, never against the source paper's published effect after decay. Computed afterwards ([`../tools/power_first.txt`](../tools/power_first.txt)): the decision tests of Studies 003 and 004 could see a timing edge of about 1.7% a year at 80% power over 185 and 180 months, and an edge of 1% a year or less would usually have been missed; Study 005's in-sample check could see 4.4% a year ([METHODS §1.2](../METHODS.md#12-power-stated-before-the-result)); the forward records of Studies 006–008 can see about 4.8% a year over 60 periods, and the Study 009 pool 2.75% a year at long-history dispersion, against the +0.70% a year the three histories averaged (Study 009 §4). A long-only timing edge on liquid ETFs that survives the decay discount is more likely to sit below 1.7% a year than above it (agenda, 2026-10-24, inferred). So "not supported" from Studies 003 and 004, and "inconclusive" from 006, 007 and 009, are what those tests would say about a true edge of the plausible size as often as about none.

**Finding 2 (observed): one sample was mined three times, on a leg that then failed its fidelity check.** Studies 006, 007 and 008 ran three signals in turn (spread sign, carry rank, real-yield rank) on the same synthetic 7–10-year leg over 1969–2018, each question chosen after the previous result was seen; the agenda's own later reading is "specification search with good bookkeeping, however each step is registered" (dated addition, 2026-10-26). The leg's independent fidelity check then failed for 1969–1982: its errors flatter the three rules' differences from their exposure-matched mixes by +0.63%, +0.57% and +0.77% a year in those years, a quarter to a third of the rules' own edge over the months checked ([`../tools/fidelity_stocker.txt`](../tools/fidelity_stocker.txt); agenda, 2026-10-26 05:2xZ). The two "inconclusive (fragile)" verdicts, t 2.06 and 2.10, sit on a leg whose known bias is of the order of the effect.

**Finding 3 (observed): two studies spent themselves on data construction and produced no evidence about any rule.** Studies 001 and 002 built and rebuilt a synthetic pre-2002 bond series and halted at their own gates (tracking error 1.540% then 1.145% against a 1.5% limit and a mean gap of +0.455% then +0.451% a year against ±0.40% in 001; tracking error 2.02% against 1.5% on 2003–2015 in 002). Both were independently reviewed and both were right to halt. The cost is that the programme's first two studies tested a data product, not a hypothesis, and the hypothesis they were built for (the term-spread switch) was then run on a different synthetic leg in Study 006, with Finding 2's result.

**Finding 4 (observed): the first two questions chosen by power found the first clear effects, and both failed on a reason their own notes had written down.** Studies 010 and 011 were the first fixed under the power-first rule, on the Kenneth French Data Library's US history because it was "the only sample the desk can read without purchase or sign-up that is long enough to see an edge of the size this programme has observed" (agenda, 2026-10-26 06:2xZ). Both found effects the ETF-era tests never could: a timing difference of +2.57% a year, t 3.78, over 1,190 months (010), and +3.45% a year long-short, t 2.04, over 806 months outside the paper's sample (011). Study 010 failed because the gain over the rule's own average position was no gain over holding the four factors long (Sharpe 0.575 against 0.554; the timing earns about what it gives up by not holding the premia), which its own pre-registration (§2, "why it might not survive here", point d) had predicted: "most of its gain may come from holding winners long, which B3 partly holds too". Study 011 failed its deflated-Sharpe criterion (0.935 against 0.95), keeps under a third of the gain at 50 bp costs and has no decade from the 1970s on with t above 1.30: the shape of a published edge after publication, which is what [MP16] says to expect and the note's §2, point b, names ("the months after it are the period in which the rule was public from 1999"). Power was the right first filter. It was not a sufficient one: neither note had to say, before the run, why the edge should still be there, or how it would fail against the exposure-matched benchmark, so the predicted failure modes were disclosures rather than reasons to choose a different question.

**Finding 5 (observed): six studies' result files were built from data the repository may not publish.** On 2026-10-30, 26 files computed from Tiingo or Alpaca daily bars were removed from the tree (the 003 and 005 monthly returns, the 004 index and signal tables, the 006–008 episode and actual legs; [`../tools/vendor_series_removed.md`](../tools/vendor_series_removed.md)), and the pre-FOMC drift candidate (planned as Study 012) closed on the market-data terms after its power had been computed and it had been queued. The reviewers' recomputation of Studies 003–006 no longer runs in CI. No question was chosen with the source's terms read first; the terms were read on 2026-10-27, after eleven studies and eight power checks.

**What the programme kept choosing (inferred from Findings 1–5).** Textbook signals from the papers everyone has read (12-month trend in 003, 004 and 007's T3; the term-spread sign in 001, 002 and 006; carry, value, factor and industry momentum), each with a decay literature the agenda cites, tested on a sample too short to see the decayed edge (the ETF era), or on one long sample three times, or on the paper's own history. Each study's "why the edge might exist" section repeated the source paper's reason; none stated a reason the edge should survive publication in the decision sample, and none was required to. Power came first from Study 006 on, but was measured against the programme's own bar rather than the paper's decayed effect; persistence and publishable data never came first. The baseline the programme ignored is its own agenda: §2 said what to expect of a published edge before any study ran, and no bar was set against it.

**What was right.** Every verdict is honest and reproducible, every miss of the method (the fidelity failure, the mined leg, the power gap, the licence exposure) was found by the programme's own checks and written down with a date, and the negative results on the ETF-era rules are evidence of the kind an allocator rarely sees published. Study 005 did state its power before the run and read its own result correctly as a refutation. The power-first rule, once adopted, closed eight candidates in two days that would each have been another uninformative study.

**Changes (built and tested 2026-10-31):**

1. *The question gate.* From Study 012 on, a question is fixed only when its `QUESTION.md` carries a "Question gate" section with four labelled statements, checked on the committed files by [`../tools/check_question_gate.py`](../tools/check_question_gate.py) in `make lint` and CI: **Power ratio**, the decision test's minimum detectable effect at 80% power divided by the published effect, at most 0.50 to run as a test (a stated choice from [MP16]'s post-publication figure of about 42% kept), 0.50 to 1.00 only as a labelled low-power check, above 1.00 not run; **Persistence**, why the edge should still exist in the decision sample after publication and how the rule would fail against its exposure-matched benchmark ("the paper found it" is not a reason); **Data terms**, the source's terms read on a stated date, or which files will be withheld and how a reader regenerates them; **Unmined**, that the scored months were read neither by the source paper nor by an earlier study of this programme on the same rule family, or the test is labelled a replication. A pre-registration in a folder without a passing question note fails the check. Studies 001–011 are exempt and reported as such.
2. *Which of the four each finished study would have met (observed from the notes, for the record, no verdict changes).* Power ratio: none of 001–005 (no power before the question); 006–011 had a minimum detectable effect committed before the question, against the programme's 2%-a-year bar or the pool's observed Sharpe, never against the source paper's effect, so the ratio was never computed. Persistence beyond the paper's reason: 005 only (a mechanism of its own, from the programme's evidence). Data terms read before the fetch: none. Unmined months: 010 (432 months before its paper's sample) and 011 (806 outside it); 006–008 mined the same leg; 003–005 used a window the model's general knowledge covers (METHODS §4).
3. *Sample before signal.* The agenda's next candidate is chosen by sample first (an unmined window the desk may publish, long enough at 0.50 of a published effect), then by the signal with a persistence reason on that sample; recorded as a dated addition in the agenda before any question note.

**Still unknown.** Whether any of the rules has an edge of the decayed size: the forward records (003–008, 009, 010, 011) are the only tests that can say, and none can see it under about 60 months. Whether the 0.50 threshold is right: it comes from one meta-analysis of cross-sectional equity predictors and is applied here to timing rules and to long-short portfolios alike; a dated addition may change it before a question is fixed, never after. Whether a question that passes all four statements exists on data the desk may read and publish: the eight power checks since Study 011 found one candidate at 0.77 and none at 0.50.
