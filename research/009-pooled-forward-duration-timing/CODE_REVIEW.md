## Report (verbatim; the reviewer's start 03:20:22 UTC, end 03:24:47 UTC)

FAIL

Two must-fix problems: a test can carry out the one-time scoring on the real repository, and the scoring-date gate trusts member dates that nobody checks. Both are small to fix. The core logic matches the pre-registration: keying, block, exclusion, Newey–West with 6 lags, the verdict rows, K and the ×12 annualisation all hold.

1. **must-fix**, tests/test_pool.py:207-213. `test_main_refuses_on_the_real_repository_today_and_writes_nothing` runs `pool.main` against the real `RESULT_JSON`, the real `trials.md` and the real `shadow.csv` files, with made-up verdicts (all "inconclusive (forward)", scoring dates 2031-11-03). Scenario: in about 2031 all three `shadow.csv` files have 60 or more rows, the "Scoring date (P1)" row is in `trials.md`, and 006 is testable. A local `make test` then writes the real `results/score.json` from fake member verdicts. That uses up P1's single scoring, and every later honest run is refused with "scored once". The `existed` assert fails only after the file is already written. Fix: monkeypatch `RESULT_JSON` to `tmp_path`, or `pytest.skip` when any member's `shadow.csv` exists.
2. **must-fix**, pool.py:165-178. Each member's `scoring_date` is taken from the hand-written JSON without any check. In all three members' code, `scoring_date` is the 61st ok record's execution date, which is the `period_end` of `shadow.csv` row 60. That value is in the file but never compared. Scenario: with every member's date set to "2026-01-01" and a `trials.md` row dated 2026-01-02, the probe scored "inconclusive" without complaint. The test fixtures show the same gap: member dates are 2031-11-03, but the constructed blocks end on 2031-12-02. Fix: in `block()`/`score()`, require `member_verdicts[m]["scoring_date"] == block(m).iloc[59]["period_end"]` for every member. In `main()`, also refuse when the logged date is later than today (UTC). Validate dates with `date.fromisoformat`; the current check accepts "2031-99-99".
3. **should-fix**, pool.py:177. The check is `when < last_member`, so a scoring date equal to the last member's date passes. The pre-registration says "follows", and the design review recommended "has passed". The `precedes_le` mutation survived, so no test pins this boundary. Fix: decide strict or equal, write it in the code and add a test at the boundary.
4. **should-fix**, pool.py:84. The regex `[^|]*` accepts any text after "Scoring date (P1)" in the step cell. Scenario 1: "| Scoring date (P1) postponed, not yet fixed | 2031-12-01 |" is read as the scoring date. Scenario 2: `trials.md` rows are append-only, so a later "Scoring date (P1) correction" row makes the code refuse permanently with "more than one". Formatting variants (bold, backticks, a leading indent) return None, so they fail safe. Mentions in other cells are correctly ignored, but no test covers that (the `regex_unanchored` mutation survived). Fix: match the step cell exactly (`\|\s*Scoring date \(P1\)\s*\|`), and add tests for the variants.
5. **should-fix**, pool.py:111-117. `check_006` compares only testable versus "not testable". A stated 006 "supported (forward)" on a noise file is accepted and then published in `member_verdicts`, which §3 says is shown beside P. 006's full verdict can be worked out from `d` and `T1_holding`. Fix: recompute 006's whole row with `newey_west_mean(d)` (default lags), using the same rule as `forward.py:332-346`, and refuse on any difference. The check does not wrongly refuse when a holding cell is empty, because `nunique` ignores NaN on both sides (probed).
6. **should-fix**, pool.py:216-221. If a verdict entry is not a dict (for example `{"006": "x"}`), `score()` raises `AttributeError`. `main()` does not catch it, so the user gets a traceback instead of "refused". Fix: validate the JSON shape, or catch `AttributeError`/`TypeError`.
7. **note**, pool.py docstring lines 13-17. The claim that shadow.csv does not carry 007/008's weights is only partly true. Their `shadow.csv` has `w_T1`, the weight held each period. A one-way check is possible: if the member says testable but `w_T1` is constant over rows 1-60, refuse. Optional.
8. **note**, tests/test_pool.py:109-114. The slip test moves only row 10's `execution_date`. In the members' real files, `append_shadow`'s continuity rule means a slip also moves row 9's `period_end`, so two rows drop, not one. The code handles the realistic case (the probe gave n=58), but the test does not model it.
9. **note.** If all three members miss the same month, the two-month period has the same key in every member, so it enters P (the probe confirmed this). It is then annualised ×12 as if it were one month. This follows §2's literal rule; the report could disclose the count of multi-month periods.
10. **note.** "low-power check" appears only in the `label` field and the printed line, not inside the verdict strings. That matches the pre-registration's "part of every row's label" only if the publisher always shows the label.
11. **note.** Smaller test gaps, each a surviving mutation: `check_006` over rows 2-60 instead of 1-60 is not caught; removing the sort of `common` is not caught (harmless while the files are in date order, but Newey–West depends on the order); the members' date-format check is untested.
