# Predictions ledger

The desk's market calls, written down before the outcome and scored when due. The point is not the hit rate of five calls; it is that a reader can check that nothing was edited after the fact and that misses are recorded like hits.

Files:

- `ledger.csv`: one row per call, **append-only**. Columns: `id`, `made_on`, `series` (a FRED series id, or a derived id defined in `score.py`), `statement`, `test`, `threshold_low`, `threshold_high`, `due_on`, `confidence` (the desk's own probability), `basis` (why, and the downside case). A row's git history shows when it was added; a row is never changed. If a call turns out to be badly specified, a new row says so and the old one is scored as written.
- `score.py`: scores every due, unscored call against the public series, once, and appends to `outcomes.csv` with the observed value, the observation date and the hash of the data file it used. It never writes to the ledger and refuses to score an id twice. Test kinds are defined in its docstring.
- `outcomes.csv`: created by the first scoring run. A miss is written like a hit.
- `manifest.json`, `raw/`: provenance of each scoring fetch; `raw/` is not committed.
- `baseline.py`, `baselines.csv` (added 2026-10-25): a second, market-anchored probability for every call, computed by the frozen method in `baseline.py` from public data as of the last observation the view used, written before the outcome; **append-only**, one row per id, a second attempt is refused. `baseline.py --summary` writes `SKILL.md`: the desk's Brier score beside the baseline's, so the ledger is judged on skill over the market, not on a bare hit rate.

The desk's confidence figures are honest probabilities, not hedges: over many calls, those marked 0.65 should come true about two times in three. With five calls nothing can be said about calibration yet; the ledger is built to be judged once it is long enough.

The calls themselves, and the reading of the data behind them, are in [`../desk-view/DESK_VIEW.md`](../desk-view/DESK_VIEW.md). The view is updated weekly; each update appends new calls here, writes their baseline rows with `baseline.py --asof <view's market-data date> --ids <new ids>` in the same commit, and runs `score.py` for any that are due, then `baseline.py --summary`.

Nothing here is investment advice. The calls are written to be falsified, and some will be.

## Market-anchored baseline (dated addition, 2026-10-25)

The [cold read](../COLD_READ.md) (point 3) said a hit rate on range calls means little when the market already prices them. Agreed. From 2026-10-25 every call carries a second probability in `baselines.csv`, computed by `baseline.py` by a method fixed in that file before any later call was written:

- policy-rate calls: the 4-week bill minus the effective funds rate, scaled to the meeting day and divided by the hike step (FRED has no futures; the bill-funds basis is ignored, which is the method's main weakness);
- yield and slope levels on a date: a normal distribution centred on the forward level read off the par curve, with the trailing-year realised daily volatility as the scale (realised, not option-implied: FRED carries no implied-volatility series, so the width is a proxy);
- "stays inside a band every day": seeded random-walk paths with the same scale;
- the stock-bond correlation proxy, which has no market price: the historical persistence of its sign, labelled a base rate.

Every input, the observation dates and the hash of each file used are in the row. `SKILL.md` lists desk and baseline probabilities side by side and, once calls are scored, both Brier scores and their difference; with fewer than about thirty scored calls the difference is descriptive.

**Disclosure.** The method was designed on 2026-10-25, two days after the first five calls were logged, so their baselines are retrospective: computed from observations to 2026-10-21 only (the view's market-data date), but by a method chosen after the calls existed. A reader may discount them for that. For calls from the 2026-10-30 view onward the baseline row is written in the same commit as the call. What the retrospective rows say: the 4-week bill on 2026-10-21 (3.92% against funds at 3.88%) priced about a one-in-five chance of the 28 October hike the desk put at 0.70, so V1 is a call against the market, scored on 2026-10-29; the forward curve put V2 and V3 close to the desk's figures (0.66 and 0.59 against 0.65 and 0.60); the breakeven band of V4 is wide against realised volatility (baseline 0.95 against the desk's 0.75, so a hit there earns little); the correlation call V5 has a base rate of 0.70 against the desk's 0.65.

## Scoring waits for the due date's print (dated addition, 2026-10-28)

Found before any call was scored: `score.py` treated a call as due on its due date and, when the fetched series had no value for that date, used the last earlier observation. Run on 2026-10-29 before FRED posts that day's row, it would have scored V1 on the 2026-10-28 value (upper limit 4.00%, the day of the decision) and written a permanent miss, since a call is scored once. A dry run on a throwaway copy with the live FRED file at about 17:25Z on 2026-10-28 (`--today 2026-10-29`, series ending 2026-10-28) did exactly that. The scorer now requires the series to hold a row dated on or after the due date (FRED writes an empty row on holidays; the derived correlation series drops empty days, so a later row counts); until then it prints `NOT SCORED ... retry on a later day` and writes nothing. The same dry run with the fix refused V1. When the due date's own value is empty, the last valid value before it is still used and named. No ledger row, threshold or due date changed; `outcomes.csv` does not exist yet.

## Rules after the first miss (dated addition, 2026-10-30)

V1 (a 28 October hike at 0.70) missed; the baseline had it at 0.21. The post-mortem is in [`POST_MORTEMS.md`](POST_MORTEMS.md): the desk read a 37 bp 3-month bill spread as "one hike plus part of another" when two full hikes could have produced at most 34.6 bp of it, and never looked at the 4-week bill, which carried the October meeting alone and showed a fifth of a hike. From this date:

- **Baseline before confidence.** The baseline row is computed on the draft call (`baseline.py --asof <view date> --ids <id> --dry-run`) before the confidence is written, and committed with the call. A confidence more than 0.20 from the baseline names the baseline in the basis and says, in one testable sentence, what the market is missing.
- **Nearest instrument.** A meeting is read off the bill maturing soonest after it. A longer bill's spread is decomposed across every meeting inside its life and compared with `baseline.max_policy_spread`; the excess is premium and is called premium. The recent bill-funds basis is quoted beside the reading.
- **Brier every week.** Each desk view reports the desk's and the baseline's Brier scores and the number of scored calls from `SKILL.md` (held by a tool since 2026-11-11: the section below).
- **The no-change path is a named downside** of every policy call.

The first two rules are enforced on the committed files by [`../desk-view/tests/test_ledger_discipline.py`](../desk-view/tests/test_ledger_discipline.py) for calls made on or after 2026-10-30; the five calls of 2026-10-23 are exempt and stand as logged.

## A row's shape is held against its test kind (dated addition, 2026-11-09)

- **Every column of a call is held before anything is scored.** No tool writes a rates call (none will be: the programme moved to prediction markets on 2026-11-01 and this ledger runs only until V2–V5 score), so the gate a hand-typed row meets is `score.row_shape_violations`, applied by `score.read_ledger` at scoring time and by [`../desk-view/tests/test_ledger_shape.py`](../desk-view/tests/test_ledger_shape.py) on the committed file: a two-sided test (`between_on_due`, `within_every_day_until_due`) carries both thresholds with low below high; a one-sided test carries no `threshold_high`; the series is one the baseline can price (`baseline.SERIES_SPEC`); statement and basis are not empty; the confidence is a probability in (0, 1) with two decimals; dates are `YYYY-MM-DD` with `due_on` after `made_on`; ids are unique. `score.evaluate` refuses a band it cannot read instead of scoring it. Until this date an empty `threshold_high` on a two-sided test scored a silent miss (`between_on_due`) or a silent hit (`within_every_day_until_due`): see [`POST_MORTEMS.md`](POST_MORTEMS.md) "A band with one side scored as a result". The five committed calls pass unchanged.

## A scored row is held against the call it scores (dated addition, 2026-11-10)

- **Every column of an outcome and of a baseline is held against its ledger row, at the writer and at the reader.** `outcomes.csv` and `baselines.csv` are written by `score.py` and `baseline.py` only, and until this date neither reader held a row: `baseline.skill_summary` counted any non-empty `result` that was not the word `hit` as a scored miss, an empty result left a call "not yet due" in `SKILL.md` for ever while `score.due_unscored` treated it as scored, an id the ledger does not carry was dropped from the table while the call was scored again into a second row, a repeated id doubled the call in the Brier, a `baseline_probability` of 1.5 gave a Brier of 2.25 in silence, and nothing compared a baseline row's `desk_confidence` with the ledger's confidence or its `asof` with the call's `made_on`. Now `score.outcome_row_violations` and `baseline.baseline_row_violations` are the one list of sentences per record, each naming the id and the column: an outcome's `result` is `hit` or `miss`; its id is one ledger id written as the ledger writes it and appears once; `made_on <= observed_on <= due_on <= scored_on`; `observed_value` is a finite number; the note is not empty; `raw_sha256` is one or more digests joined by `;`. A baseline's `method` is the frozen method for the call's series and test (`baseline.expected_method`, held to `compute_baseline` by a test); `baseline_probability` is in [0, 1] with four decimals; `desk_confidence` equals the ledger's confidence, so a call edited after its baseline was written is caught; `asof <= made_on` and `asof <= computed_on`; `inputs` is a JSON object carrying `h_business_days`. `read_outcomes`, `read_baselines`, `append_outcome` and `append_baseline` take the ledger and apply the list; `skill_table` refuses a stray or repeated id and a result it cannot read instead of merging past it; `skill_summary` refuses a probability outside [0, 1]; `tools/check_due.py` counts a row as a score only when its result is `hit` or `miss`, so any other row leaves the call `DUE` by name. [`../desk-view/tests/test_record_shape.py`](../desk-view/tests/test_record_shape.py) keeps the column search on both records (every column classified with one bad value and the word its refusal must carry) and runs the committed files through the readers. See [`POST_MORTEMS.md`](POST_MORTEMS.md) "A result spelled another way was a miss". The committed rows pass unchanged and `SKILL.md` regenerates byte-identical.

## A figure copied onto a page is held against its record (dated addition, 2026-11-11)

- **The desk view's Brier line is printed from the record and held to it, never retyped from `SKILL.md`.** The 6 November view carried "baseline 0.046", a round by hand of SKILL.md's four-decimal 0.0455; the record's figure is 0.04549689, which is 0.045 at the three decimals the view prints, and for five days nothing read the line back: the "Brier every week" rule above had prose and no check. Now `baseline.view_brier_clause` renders the clause (`<n> scored call(s); desk <p>, baseline <p>, skill <s>`) from the unrounded summary that `skill_summary` computes through the three records' gates, and `baseline.view_brier_violations` holds the one line of `desk-view/DESK_VIEW.md` that begins "Brier against the market-anchored baseline" to it: the count, and each figure equal to the record's figure at the decimals the line itself prints (all three alike; the skill is the record's difference rounded, not the difference of two rounded figures); with no scored call the line carries no figure. [`../tools/check_view_brier.py`](../tools/check_view_brier.py) applies it in `make lint` and CI and prints the clause to paste with `--print`; [`../desk-view/tests/test_view_brier.py`](../desk-view/tests/test_view_brier.py) holds the renderer, the alterations and the committed page. See [`POST_MORTEMS.md`](POST_MORTEMS.md) "A Brier figure rounded twice". The page's digit was corrected on 2026-11-11 with a dated note under the line; `SKILL.md` and the records were not touched.
- **`SKILL.md` is a regeneration, held equal to one (same day, 12:15Z).** The page is written only by `baseline.py --summary`, and until this date the committed copy was held current by the runs' habit of regenerating it with `--dry-run` and comparing by eye: on the committed tree a digit edited on the page, or a score written without the page, passed every test and check (shown on 2ace7a9 before the change). Now `baseline.page_text(today, …)` is the one function the writer and the check call; [`../tools/check_skill_pages.py`](../tools/check_skill_pages.py) in `make lint` and CI reads the page's own "Generated by `predictions/baseline.py --summary` on <date>" line (exactly one, the generator named, the date YYYY-MM-DD, not after today and not before the newest row of the three records, `baseline.records_newest_day`), regenerates the page at that date in a fresh interpreter from this folder and holds the committed bytes equal to it, naming the first differing line, page beside regeneration, and the command that rewrites it. The date is held only to its bounds. [`../desk-view/tests/test_skill_page.py`](../desk-view/tests/test_skill_page.py) holds the committed page, the date, `--summary --dry-run` printing exactly the page, and four alterations named by line. The same check holds [`../pm-view/SKILL.md`](../pm-view/SKILL.md). Since 2026-11-13 (18:15Z) the four alterations are built from the page as it stands and the builders are also run against a page regenerated from the record's next state (every call scored): a test of a committed record takes its expectation from the record or from the rule, never from the record's value on the day the test was written; until then the test held the page's 29 October figures and line numbers and would have failed for no defect on the first run after 31 December ([`POST_MORTEMS.md`](POST_MORTEMS.md), "A test that held the page to the day it was written").
